# read_page 与上下文工程：一次完整讨论的整理

> 讨论时间：2026-10-04
> 主题：Automa 的 agent runtime 在「读网页」这件事上，上下文会不会爆、怎么省 token、
> 以及什么样的表示法能让模型写出正确的操作代码。
> 所有数字均为实测（真 Chromium 跑真页面 / 项目自带 estimator），标注为推断的除外。

---

## Q1 上下文会爆吗？——会，且是现在就能复现的

用 `src/agent/window.js` 模拟单轮 send 的 wire 形态（12 步 = 12 次 `read_page`）：

| 单轮步数 | 估算 token | 阈值 25,600 | 实际丢弃 |
|---|---|---|---|
| 1 | 10,416 | 未超 | 0 |
| 3 | 31,208 | **超** | 0 |
| 6 | 62,395 | **超** | 0 |
| 12 | 124,769 | **超 4.8 倍** | 0 |

第 3 步起越线，`applyTokenBudget` 一条没丢，超标请求直接发给 provider（400）。

**为什么 Web Agent 比通用 coding agent 更容易炸**：
- `read_file` 读人写的源码，信息密度高；`read_page` 读的是渲染后 DOM，HTML 属性/URL/
  JSON 标点这些 BPE 效率极低（`window.js:6-10` 自记「系统性低估 40–47%」）
- 元素级操作必需结构化数据（重复项检测、交互元素索引），这部分省不掉
- `prompt.js` 鼓励自纠（写方案前重新 read_page 确认），每自纠一次多吃一份完整快照

**四层防线，漏了两层**：

| 层 | 状态 |
|---|---|
| ① 保守估算（1.5 / 0.7 字符每 token） | ✅ 已接 |
| ② 单观察值 8K 截断 | ✅ 已接（`events.js:79`） |
| ③ 陈旧页面快照剔除 | ❌ **写了、测了、没接** |
| ④ 整轮裁剪 | ⚠️ 接了，但单轮内结构性失效 |

- **根因三**：`elideStaleObservations` 全仓只有定义和两个测试，生产链路（`loop.js:321`、
  `wire.js`）都没调用——技术方案 §4.2 原文写「在 buildWire 时做」，实现漏了。
  实测接上省 **90%**（124,769 → 12,145）。
- **根因四**：`dropOldestTurn` 的丢弃单元是 `(user, assistant, tool*)` 整组，且硬性保护
  最后一个 user。但单轮 send 的 wire 全轮只有 index=1 一个 user，第一个候选就撞上
  `i >= lastUserIdx` → break。12 步全在同一轮内，没有可丢的单元。
  ⚠️ `window.test.js:156` 把 `dropped===0` 固化成了「预期」，测试反而掩饰了这个缺口。

## Q2 方案说人话：旧照片作废

不是让 agent 少读网页，而是**旧照片作废**：像电话里指挥看不见屏幕的同事写选择器，
他每步都拿到一张网页照片，做到第 12 步手里攒了 12 张。第 1 步那张早没用了——
他第 3 步说的话早就吸收了。现在的问题是 12 张一张没扔。

**为什么不能直接删掉旧消息**：OpenAI 规矩是模型说过「调这个工具」就必须配一条工具结果，
少一条整个请求直接报错。所以方案是**留壳子、换内容**：消息还在、`tool_call_id` 还在，
8000 字的网页内容换成一行「此前的页面快照已被压缩」。这就是省 90% 的来源。

**丢的是过程、留的是结论**：旧快照是「第 3 步时网页长什么样」，是原材料；模型第 3 步
说完话后，有用的结论（selector、条数）已经写在它自己的回复里，那部分不被压缩。
唯一风险是模型当时没把关键结论说出口——靠 observability 兜，比现在爆掉强。

## Q3 第二轮对话还要不要 read_page？——留指纹，别装监控

不读的前提是「确认过页面没变」，而这个确认必须几乎免费。直觉是装 MutationObserver，
**不推荐**：轮播图、实时数据在滚 → 触发重读 → 等于没省。更好：每次读页面顺手算指纹
（URL+标题 / 元素总数 / 可见文本长度 / 文本采样 hash），前三个浏览器有缓存，成本近零。

**现状盲区**（已核实 `index.js:250-286`）：`preStepNotice` 只比 `origin`——跨站跳转 ✓，
**站内 SPA 换路由、翻第 2 页 ✗**，筛选/展开/懒加载 ✗（连 URL 都没变）。
**跨轮根本没人检查**：会话存储里没留指纹，第二轮 send 纯凭历史快照在猜。

**一个隐蔽的坑**：指纹不能塞进 `<untrusted_page_content>` 观察值文本里——一旦启用
「旧快照作废」，那些内容会被替换成标记，指纹跟着一起没了。必须放在 `TOOL_RESULT`
事件的**独立字段**上。

**更聪明的做法**：与其让模型猜要不要读，不如让「瞥一眼」变便宜——加 `detail:'probe'`，
只回 url/标题/元素数/指纹，约 150 token，每步都 probe 也不心疼。
原则沿用 `preStepNotice` 的「advisory 而非闸门」：runtime 不替模型决定读不读。

## Q4 只截断 8000 字合理吗？——不合理，且正文实际只有 3000

三层截断，最狠的是第一层：

| 层 | 上限 | 位置 |
|---|---|---|
| 可见正文 | **3000 字** | `handlerAgentReadPage.js:17` `MAX_TEXT_CHARS` |
| 整个观察值预算 | 8000 字 | 同文件 `:389` |
| 发送前硬截 | 8000 字符 | `events.js:79` |

四个毛病：**从头截**（运费/退换货政策天然在页面底部，结构性找不到）；**静默降级**
（模型再读一次拿到的还是头 3000 字，死循环）；**超预算砍错东西**（砍掉交互元素索引
只留正文，而找东西时恰恰是按钮/链接文本最有用）；**根本的一点：截断不是压缩**。

**正解：别把整页搬上来，让页面自己去搜。** 现有工具箱（`tools/index.js:44-57`）里
没有任何一个能「按文本内容找元素」——模型是被逼着用全文的。加 `find_text`：
给关键词，content script 在页内搜，只回命中几条（带 selector + 前后片段）。
不丢东西、便宜 8 倍、命中即带 selector 可直接接 `highlight_selector` 闭环。
实现成本低：`cssPath(el)` 现成（`:54`），约 40 行 + 工具定义 30 行。

## Q5 业界怎么把网页喂给 AI（调研结论）

**先纠正前提**：Automa 不是 raw HTML 直喂，吐的已是结构化摘要，起点比大部分选手高。

- **表示层**：Playwright MCP 用可访问性树，官方口径 200–400 token/快照 vs DOM/截图「数千」；
  Firecrawl 转 markdown 只取主体，15 页 4,103,706 → 190,817 token（**21.5×**），
  其中 5 页 raw HTML 超 200k 直接放不进窗口。
- **裁剪层**：arXiv 2511.19477 用 flash-lite 小模型先筛再喂大模型（保全部交互元素、
  重复列表留前 5 项 + 分页控件），长流程成本 −57%；Anthropic `clear_tool_uses` +
  compaction 三件套。
- **增量层（最大杠杆）**：Altair 同 tab 同 URL 只发 unified diff，HN 点搜索框
  3,690 → 80 token；98 步真实对话 355K → 151K（−58%），留在同页的动作 −82%。
  规则：跳转/新 tab/显式 read 才发全页；改动超一半发全页；「没变」是有效信号。
  Zooz 博客验证了「rich 的当前观测 + 哨兵的老观测」才是对的，naive 砍短描述性能反崩。
- **记忆层**：browser-use `extract` 单独起轻量 LLM 按 schema 抽，主上下文只拿结果；
  WebGenie 用 `layoutHash` + `SelectorAnchor` 跨会话复用 selector，`FailureRegistry`
  同 selector 失败 >2 次标 BLOCKED 防死循环。

**不能照抄的**：Playwright MCP 的 `ref=e5` 体系（见 Q6）、coordinate clicking。

## Q6 两条约束下哪个方向更好？ref 为什么不行？

约束：① 读完页面能写出正确的操作代码 ② token 尽量少。

**先纠正之前的说法**：「ref 结构树不行」不准确，要拆两层——
**a11y 树（表示层）能抄且实测更省；ref（寻址层）不能用**。

### ref 不行的三条硬证据（读码确认）

1. **落盘位置不认它**：agent 经 `add_block`/`update_block`（`tools/canvas.js`）写块 `data`，
   交互块 selector 落在 `data.selector`，类型由 `data.findBy` 决定。ref 是一串 `e5`，
   没法写进这个字段。
2. **运行期引擎只有两种**：`handleSelector.js:36-37` 走 `FindElement[data.findBy]`，
   `src/utils/FindElement.js` 只有 `cssSelector` 和 `xpath`，底层 `querySelectorAll`。
   `ref=e5` 不是合法 CSS → 不是「退化」，是「永远不命中」。
3. **生命周期对不上**：ref 绑在生成它的那一版快照上，页面一变就失效；Automa 的产出物
   要在几天后另一次页面加载里跑，中间没有快照可依附。

### 表示法实测（同一批 24 个交互元素，口径用项目 `estimateTokens`）

| 表示法 | token | 相对现状 | 带 selector |
|---|---|---|---|
| A 现状 Automa 索引 | 960 | 100% | ✓ |
| B a11y 树+ref | 552 | 57% | ✗ ← 被约束①一票否决 |
| C 地址优先紧凑表 | 734 | 76% | ✓ |
| D JSON | 1552 | 162% | ✓ |
| E 极简 selector+短文本 | 657 | 68% | ✓ |

B 最省但被排除 → **「换表示法」不是主杠杆**。

### 真正的主杠杆：预算分配

现状单次 `read_page` = 正文 2000 + 索引 960 = 2960 token，**正文占 68%** 而对「写
selector/操作代码」几乎无贡献。改成片段 + 地址表 = 868，**单次 −71%**。

**结论一句话：`read_page` 从「读内容」改成「给地址，内容按需取」。**
排序：①预算迁移 ②按需取内容（find_text / resolve_selector）③增量（diff/指纹）
④旧快照作废（已定 P0）。
不做：全文 a11y 树替换、JSON、ref、坐标点击。
登记不做的候选：语义化选择器（`:has-text()` / `getByRole`），抗 DOM 重构但要扩 `FindElement`。

## Q7 真页面实测：books.toscrape.com（详细版见 `docs/agent-readpage-trace.md`）

在真 Chromium 里把 `handlerAgentReadPage.js` 跑在该页面上，实测发现**五个具体问题**：

| # | 问题 | 证据 |
|---|---|---|
| P1 | 索引预算被布局吃掉：`MAX_INTERACTIVE=60` 按文档顺序取，60 条里 **53 条是侧栏分类导航**，书元素从 [54] 才出现 → 只露出 4 本 | 交互元素索引 [1]–[53] 全是 `a "Travel"` 等 |
| P2 | 书名取 `textContent`，长书名被站点截断；真名在 `title` 属性 | `[55] a "A Light in the ..."`，而 title 属性是 `A Light in the Attic`——**静默错误，短书名正常所以难察觉** |
| P3 | 正确的列表被噪声压在第 3 位 | ×50 侧栏导航排第一，×3 登录表单第二，**`ol.row` ×20 才是书列表**，后面 3 条星级图标噪声 |
| P4 | 字段名是无语义标签名，链接是相对路径没标注 | `字段 product_pod / a / product_price / ...` |
| P5 | 超预算砍错地方：`maxChars≤3200` 实测交互索引**整块消失**，正文一个字没砍 | 输出 3359 字符里除重复项检测外没有任何可用 selector |

**agent 为什么还是写对了**：靠模型从碎片里拼（重复项检测给了 `li.col-xs-6...`，正文里有
£51.77 可辨认），**不靠工具**。侧栏在内容区之后 / 字段不可辨 / 模型弱一点的场景就会静默写错。

### 原型实测（同一真页面）

| 方案 | 字符 | token | 相对现状 |
|---|---|---|---|
| 现状 `detail:'auto'` | 6705 | 4470 | 100% |
| 原型「地址优先」 | 4636 | 3091 | 69% |
| **原型「列表模式」（+单条样例）** | **455** | **304** | **−93%** |

列表模式 304 token 里装了写出正确 JS 需要的一切：单项 selector、书名（title 属性）/链接/价格
三个字段的取值路径、样例值、条数、「其余相同」的显式声明。

**印证**：列表任务里逐条展开元素是纯浪费——20 本书结构一样，展开 24 条和 1 条信息量几乎相等，token 差 6 倍。

### 改造清单（按文件，详见 trace 文档 §5）

- `handlerAgentReadPage.js`：R1 列表模式段（取代逐条展开）R2 导航折叠不占预算
  R3 name 兜底顺序改 title→aria-label→placeholder→textContent R4 重复项按信息量排序
  R5 正文默认不输出 R6 降级砍明细不砍样例
- `tools/page.js`：detail 口径从「读多少正文」改成「给多少地址」
- 可选：`find_text` / `resolve_selector`
- 沿用 P0a（接 elide）/ P0b（单轮内淘汰）
