# 06: 预检与插话改接 pi 的注入点

**What to build:** 每步开工前的环境预检通知照旧送达模型（tab 还在吗、页面 origin 漂移了吗）；任务进行中用户补充的插话照旧在下一步开工前送达。两者都作为 **user 角色**进对话。

**Blocked by:** 01 — pi 运行时骨架

**Status:** ready-for-agent

## 验收标准

- [ ] 预检通知照旧产生，且**绝不硬停任务**（良性重定向链不能被误杀）
- [ ] 插话照旧入队、在下一步开工前送达
- [ ] **预检通知与插话都以 user 角色进对话，绝不进 system 角色**
  - [ ] 有一条测试专门钉住这一点
  - 理由：pi 在 OpenAI 兼容端点上的默认行为是「后续 system 消息全部并进 system prompt 首部」，那会把不可信内容**永久提升为可信系统指令**，比现状的「user 角色 + 标签」严格更弱
- [ ] 预检失败不杀掉整轮（现状行为）
- [ ] 插话通道坏了不挡轮（现状行为）
- [ ] 插话走 `Agent.steer()`（构造参数里传插话回调**会被框架无条件覆盖成内部队列实现**，实测确认）
- [ ] 通知文本经不可信包装，且沿用「系统侧产生」的标签 —— **注意术语陷阱**：标签名表示「事实由系统侧产生」，与「以 system 角色发送」是两件必须解耦的事
- [ ] 事件序列的变化被如实记录：预检通知现在落在「工具结果之后、下一个 assistant 之前」，与现状「assistant 与工具结果之间」语义等价但位置不同

## 备注

这一票完成的是三条红线里的第 1 条，也是三条里**后果最重**的一条 —— 违反它会把不可信内容提升为系统指令，而且不会有任何报错。

**术语上最容易搞错的地方**：项目里有个标签叫「untrusted_system_notice」，它的「system」指的是「这条事实由系统侧产生」，不是「用 system 角色发送」。现状设计（通知走 user 角色）是对的，迁移时要保持。

位置差异不是 bug，是如实记录。语义等价（都是下一轮开工前送达），但写进事件契约测试时要按新位置断言。
