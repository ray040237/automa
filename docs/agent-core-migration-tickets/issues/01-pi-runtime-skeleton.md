# 01: 建立 pi 运行时骨架，纯文本对话跑通

**What to build:** 用户发一条消息，助手流式回答一句话，过程中 UI 能看到思考、文本增量、目标页行与收尾——**不涉及任何工具调用**。这是整个迁移的第一条 tracer bullet：证明 pi 的内核能在浏览器扩展里加载、驱动、并且能把它的原生事件映射成我们的 10 种 agent 事件。

这一步刻意不含工具与确认门。它要回答的唯一问题是「pi 能不能替代我们的事件流与循环节拍」。

**Blocked by:** None (can start immediately)

**Status:** ready-for-agent

## 验收标准

- [ ] 装配层能构造出 pi 的 `Agent` 实例，`send` 一条消息能拿到流式文本回复
- [ ] pi 的原生事件全部映射到我们的 10 种 agent 事件；**映射不了的必须显式抛错，不允许静默丢弃**
- [ ] 事件顺序与现状一致：开始 → 用户消息 → 目标页 → （思考 / 文本增量…）→ 收尾
- [ ] 收尾事件带 `stopped` / `aborted` / `usage` 三项，与现状同形
- [ ] 用户中止后走正常收尾，半截已说的话留在历史里，且**不被显示成错误**（现状行为）
- [ ] 事实表构建失败时降级成空表继续对话，并发出一个 `internal` 错误事件（现状行为，不能因换内核而丢）
- [ ] 扩展能成功打包；产物体积与「换内核前」的差值记录下来
- [ ] 事件契约测试重写为对新内核的断言，且**每条新断言注明它替代的是哪条旧断言**
- [ ] 本轮跑一遍基线快照做对照，确认没有意外弄丢别的东西

## 备注

**这一步会动 `createAgent` 的实现**，不需要 feature flag —— 唯一接缝就是 `createAgent` 本身，测试通过即为新实现，不通过就 `git checkout` 回退。

与旧实现并存不是选项：维护两套循环的代价比替换一次更高，而 `git` 提供了干净的回退点。

**不要在这一票里**加工具、确认门、上下文裁剪。它们各自有独立的票，且各自有独立的静默失败模式。
