# Spec: 用 pi-agent-core 替换自研 agent 内核

状态：ready-for-agent
日期：2026-10-05
相关：[ADR 0004](adr/0004-pi-agent-core-migration.md)、[B9](backlog.md)

## Problem Statement

`src/agent` 的循环内核与 provider 层是自研的：一次「轮」= 最多 12 步 ReAct 迭代，每步一次模型调用 + 可能的工具执行；模型调用走自建的 SSE 解析与 OpenAI 兼容适配；消息历史从 agent 事件现算成 OpenAI wire 形状。

这套代码要自己维护的东西包括：SSE 分片聚合、方言 quirk、429 退避重试与配额区分、六种错误分类、悬空 tool_calls 净化、token 预算裁剪、步数上限、上下文插话队列。每一项都是踩坑踩出来的，代码里都有注释记录为什么。

同时它也有几个自建方案覆盖不到的地方：没有并行工具执行、没有输出截断保护（模型撞 max_tokens 时工具参数被截断仍会被执行）、悬空 tool_calls 的净化不够完善（不插入合成结果、不处理夹在中间的 system 消息）。

维护成本在持续增长：provider 层 430 行、SSE 153 行、主循环 561 行，加起来超过一千行需要跟 provider 行为变化赛跑的代码。

## Solution

把循环内核与 provider 层交给第三方库 `@earendil-works/pi-agent-core` / `@earendil-works/pi-ai`，保留全部产品契约。

**保留的**（不得改动其外部行为）：13 个工具的定义与 `read`/`write` 分级、确认门与 ADR 0002 的分级规则、10 种 agent 事件与观察值的 untrusted 包装、会话存储与配置、装配层。

**交给 pi 的**：循环调度、provider 适配、悬空 tool_calls 净化、并行工具执行、输出截断保护、插话队列。

**明确的取舍**：不做 token 预算裁剪、不做步数上限、错误分类降级、测试全部重写。这三项代价记在 B9。

## User Stories

### 循环与工具执行

1. 作为用户，我想助手一轮里能并行执行多个互不依赖的只读工具，这样读三个页面不用等三次往返
2. 作为用户，我想模型撞到输出 token 上限时被告知「参数可能不完整，请重新发起」而不是执行一个参数被截断的工具，这样我不会看到一个静默错误的结果
3. 作为用户，我想工具执行抛错时循环继续下去、模型能看到错误观察值并自我纠正，这样一次工具失败不会终止整轮对话
4. 作为开发者，我想工具返回值必须显式声明，这样任何裸字符串返回值都会立刻暴露而不是被静默兜底成空输出
5. 作为开发者，我想 `class: read | write` 缺失时在模块加载期就炸，这样不存在「默认放行」的路径
6. 作为用户，我想未知工具名的调用也走确认门，这样模型幻觉出的工具名不会绕过裁决

### 确认门

7. 作为用户，我想写工具执行前看到一张确认卡片，这样我不会在不知情下被改掉工作流
8. 作为用户，我想拒绝一次写操作后模型知道是我拒绝的（而不是工具失败），这样它不会换个参数反复重试同一个写操作
9. 作为用户，我想本会话内授权过的写操作不必每次确认，这样连续编辑同一批块不会被打断十几次
10. 作为用户，我想确认卡片一旦不可达就自动判为拒绝，这样我不会遇到「助手卡死」——表现与切会话、关宿主、收起侧栏完全一致
11. 作为用户，我想被确认门拦下的工具在 UI 上明确显示为「已拒绝」而不是「失败」，这样我能区分是我否掉的和系统出错的

### 安全（untrusted 包装）

12. 作为用户，我想页面正文永远包在 untrusted 标签里且标签本身被转义，这样页面里的 `</untrusted_page_content>` 不能闭合我的包装
13. 作为用户，我想工具返回、用户输入回显、tab 元数据都走同一套包装，这样注入防护不因内容来源而异
14. 作为开发者，我想 untrusted 包装在传给模型时是单个完整文本块，这样块间拼接的换行不会把闭合标签切断
15. 作为开发者，我想系统提示与通知永远以 user 角色注入，这样它们不会被框架提升进 system prompt 而获得更高信任
16. 作为开发者，我想缺 untrusted 包装时直接抛错，这样「漏注入」不会静默变成零防护
17. 作为用户，我想未包装的裸文本永远不会被发给模型，这样任何新增的事件生产者都必须显式包装

### 错误处理

18. 作为用户，我想 provider 报错时看到能区分原因的错误，这样 401（key 无效）、429（限流）、网络断了不是同一句话
19. 作为用户，我想配置缺失时报「配置问题」而不是「provider 错误」，这样我知道该去设置页而不是换模型
20. 作为用户，我想网络错误与 HTTP 错误能区分开，这样断网时不会以为 key 失效了
21. 作为用户，我想 429 配额耗尽时不要傻等重试，这样我不会对着「今日配额已用完」等十几秒再看一样的错误
22. 作为开发者，我想错误信息来自结构化数据而不是正则反解字符串，这样 provider 改文案不会让分类静默失效

### 上下文与历史

23. 作为用户，我想助手能续接上一轮的上下文，这样多轮对话不用重复交代背景
24. 作为用户，我想会话切换后旧会话的历史不被污染，这样来回切会话不会串味
25. 作为开发者，我想悬空的 tool call 在续接时被自动补上合成结果，这样被中断的一轮不会让 provider 报 400
26. 作为用户，我想上一轮被中断时能看到一条提示，这样我知道为什么对话停在那里
27. 作为开发者，我想工具结果消息夹在 assistant 与下一个 assistant 之间时位置稳定，这样提示注入的语义不因框架实现而变

### 会话与配置

28. 作为用户，我想一轮结束后 usage 累加到会话，这样我能看到这次对话花了多少
29. 作为用户，我想会话标题由模型生成且不被第二轮冲掉，这样会话列表里标题稳定
30. 作为用户，我想中途关掉助手页再打开能恢复上下文，这样长对话不会因为切标签而丢
31. 作为开发者，我想 BYOK 的 API key 加密存储且校验不过时不留任何痕迹，这样失败配置不会留下半截状态

### 可观测与运维

32. 作为开发者，我想每个 agent 事件都能追到对应的模型请求与工具调用，这样线上问题可复现
33. 作为开发者，我想日志能下载成 JSON，这样能贴给用户或贴进 issue
34. 作为用户，我想长时间无响应时能中止这一轮，这样我不会一直等
35. 作为开发者，我想中止后能知道这一轮是被中止的而不是失败的，这样 UI 不会显示成红色报错

### 打包与运行时

36. 作为用户，我想扩展的安装包不因引入新依赖而明显变大，这样我不介意这个更新
37. 作为开发者，我想第三方库只出现在一个地方，这样升级版本时只有一个地方要改
38. 作为开发者，我想第三方库不出现在我们的源码目录里，这样 lint 与仓库卫生守卫不会误扫

### 测试与可维护性

39. 作为开发者，我想每个行为都有测试覆盖，这样改内核时知道有没有破坏东西
40. 作为开发者，我想测试只测对外行为，这样换实现时测试不用跟着重写
41. 作为开发者，我想旧代码在重构期间可对照，这样出问题时能回答「这里本来是对的」
42. 作为开发者，我想重构的决策与实测依据留在版本库里，这样半年后的人不用重新跑一遍 PoC

## Implementation Decisions

### 模块边界

- **保留**：`tools/`（13 个工具定义、`validateTools` 的模块期校验）、`confirm.js`、`events.js`（10 种事件 + `wrapObservation`）、`untrusted.js`、`prompt.js`、`sessions.js`、`config.js`、`index.js`（装配层，仍是唯一允许碰浏览器 API 的文件）
- **交给 pi**：循环调度、provider 适配、悬空 tool_calls 净化、并行工具执行、输出截断保护
- **删除**：`wire.js`（pi 自己从 transcript 生成 provider 参数）、`llm/sse.js`、`llm/providers/openai-compat.js`（ADR 0003 因此被推翻，偏离理由记在 ADR 0004）
- **重写**：`loop.js` 的主循环，以及事件到pi `AgentEvent` 的映射层

### pi 侧API 的使用方式

- `Agent` 类持有 transcript、发事件、执行工具。`streamFn` 由 pi-ai 的 `Models.streamSimple` 提供
- 工具改为实现 `AgentTool`：补 `label`（必填），`execute` 签名从 `(args, ctx)` 改为 `(toolCallId, params, signal, onUpdate)`，`parameters` 用普通 JSON Schema 对象（pi 有非 typebox 回退，需实测确认）
- **返回值形状**：所有工具统一返回 `{ content: [{type:'text', text}], details, isError? }`。当前返回裸字符串的四个位置（`get_variables`、`get_block_schema` 的四处）必须显式包装 —— pi 会把缺 `content` 的结果兜成空数组，然后发出 `"(no tool output)"`，正文与 untrusted 标记一起消失且不报错
- **`class: read | write` 在 pi 里没有对应字段**，通过 `beforeToolCall` 钩子实现确认门。但 `validateTools` 的模块期 throw 必须保留 —— pi 不会替我们炸，缺 class 就等于给写操作免确认，直接违反 ADR 0002
- **工具组（`group`）也没有对应字段**，而观察值用哪个 untrusted 标签（页面内容 vs 工具结果）取决于 `group === 'page'`。这个判定必须搬进 runtime
- 确认门被拒时 pi 产出的是 error 工具结果，不是「用户拒绝」这种结构化状态。`TOOL_STATUS.REJECTED` 需在映射层自己编码（用 `beforeToolCall` 返回的 `reason` 承载内部标记）
- **插话只能走 `Agent.steer()`**：构造参数里的 `getSteeringMessages` 会被 `Agent` 无条件覆盖成内部队列实现
- **步数上限与上下文裁剪按B9 不做**。`transformContext` 钩子位置留着不接逻辑

### 三条必须写死的红线约束（违反即静默失败）

1. **untrusted 内容绝不进 pi 的 system 角色。** pi 在 OpenAI Chat Completions 上的默认是「后续 system 消息全部并进 system prompt 首部」，那会把 untrusted 内容永久提升为可信系统指令，比现状的「user 角色 + 标签」严格更弱。现状的预检通知与插话本来就是 user 角色，迁移时必须保持。注意术语陷阱：`untrusted_system_notice` 这个**标签名**表示「事实由系统侧产生」，与「以 system 角色发送」是两件必须解耦的事
2. **untrusted 包装必须是单个 text 块。** pi 会把工具结果的多块内容用换行拼接；若把观察值拆成 head/body/tail，拆分点落在标签内部时闭合标签消失，内层内容对模型裸奔，不报任何错
3. **工具返回值必须显式给 `content` 与 `isError`。** 缺 `content` 会被兜成空（见上）；缺 `isError` 而沿用现有的 `status:'error'`，模型会把失败当成功读

### 事件映射层

pi 的 `AgentEvent` 与我们的 10 种 `agent:*` 事件命名与粒度都不同，需要一层映射。映射层是纯函数，**不得吞失败**：每种 pi 事件都必须能映射到我们的某一种事件，映射不了的必须显式抛错而不是静默丢弃。

一条已知的非安全性差异：预检通知现在落在「assistant + 工具结果」组之间，pi 之后会落在「工具结果之后、下一个 assistant 之前」。语义等价（都是下一轮开工前送达），但消息序列不同，相关断言要跟着改。

### 错误处理的取舍

pi 在失败路径上只给两个可靠信号：`stopReason`（`error` / `aborted` 两值）与 `errorMessage`（字符串）。它的 `diagnostics` 字段在 OpenAI 兼容路径上恒为 `undefined`；它的 `onResponse` 回调排在重试之后，对 4xx 一次都不触发。它自己做分类靠约 60 条正则。

因此 `ERROR_KIND` 的六种分类无法完整保留。**必须显式设计降级后的映射**，并在 UI 上如实反映（不得把「配置缺失」显示成「provider 错误」）。重试显式传 `maxRetries: 3`（pi 默认是 0，即完全不重试）。

### 依赖与打包

- 运行时依赖走 npm：`@earendil-works/pi-agent-core`。本地 `pi/` 仓库只读参考，已 gitignore
- **装完必须验证产物完整性**：本机出现过 `openai` 的 ESM 产物整体缺失、只剩 CJS 的情况，症状是 `package.json` 的 `exports` 指向一个不存在的文件。判据是数 `.mjs` 文件数量 + 核对 `exports` 指向的文件存在
- 体积代价已知：完整栈比只用内核多约 414 KB（min）。记在 B9
- 第三方代码**不得**进 `src/` —— 仓库卫生守卫会递归扫 `src/agent` 与整个 `src/`，vendor 进去必红

### 迁移期的对照手段

- 基线快照：重构开始前的完整 `src/` 存放在 `.scratch/agent-baseline/`，配一个 runner 脚本。**它不进版本库**，所以重构落地时要把关键断言补成新测试，并注明每条新断言替代了哪条旧断言
- 单文件回滚：`git checkout <基线commit> -- src/agent/<file>`
- **停损点**：连续两个 ticket 出现「说不清是重构引入还是本来就有的问题」时，停下来回滚重新评估。依据是测试全部重写意味着期间没有回归保护可依靠

## Testing Decisions

**什么是好测试**：只测对外可观察的行为，不测内部实现细节。判断标准 —— 换掉实现而不换掉断言，这个测试应该照样通过。

**单一接缝**：`createAgentRuntime()` 的返回接口（`send` / `abort` / `getHistory` + 事件数组）。工具执行、确认门、错误降级、插话、事件序列全部通过它间接覆盖，不新增测试入口。

**例外**：纯函数零件保留自己的单测，因为它们不经过 runtime 且逻辑独立 —— untrusted 包装与逃逸清洗、token 预算估算、prompt 构建、会话存储与标题兜底、markdown 渲染的 XSS 断言。这些测试不受本次重构影响（实测确认），**应当尽量保持不动**。

**映射层单独测**：pi 的事件到我们 10 种事件的映射是纯函数，且是最容易出错、最该独立锁住的部分。它不引入新的运行时接缝（不是从外部调用），只是把已有接缝的内部实现拆出来测。

**重写范围**：
- 全部重写：主循环测试（39 条）、事件契约测试、装配层测试中受影响的 case、provider 层的 37 条
- 保持不动：untrusted 包装（8 类攻击面，实测独立于消息模型）、token 预算、会话存储、标题兜底、markdown、prompt 构建

**先决动作**：重写前先跑一遍基线快照，记录哪些测试在主目录通过但在快照环境跑不了（当前 10 条，属环境依赖），列成白名单 —— 否则会把「快照环境的问题」误读成「重构引入的」。

**不做**：不为 pi 的内部行为写测试。pi 自己的测试保证 pi 的正确性，我们只测「我们与 pi 的接口」。

## Out of Scope

- **不做 token 预算裁剪与步数上限**（B9 第 1 项）。若后续要补，`transformContext` 与 `finishTurn` 的钩子位置已留着
- **不接 pi 的模型目录、用量统计、缓存亲和**。当前只有一个 provider，没有多模型管理的需求
- **不改 UI**。`AgentTranscript.vue` / `AgentToolStep.vue` 的契约不变（唯一可能变的是错误分类降级后的展示，那属于「如实反映」而非 UI 改造）
- **不改 ADR 0001 的宿主结构**。两个宿主（独立助手页、编辑器侧栏）不动
- **不动 `pie-ai-agent`**。它是另一个第三方参考仓库，与本次无关
- **不修 T-55 ~ T-58**。它们是本次核查发现但独立于重构的缺陷，重构开始前应单独处理（尤其 T-55 的不安全默认兜底，迁移时极易被漏掉）

## Further Notes

**已知的坏消息要记住**：本次是「换掉内核 + 换掉 provider + 移除全部上下文护栏 + 丢掉全部回归保护」。这不是一个可以中途悄悄改主意的重构 —— B9 记了每一条的代价与重开条件。

**测试重写期间最容易犯的错**：把「新实现的行为」当成「正确行为」写进测试。重写前先跑基线快照对照，确认每条新断言在替换的是一条**曾经通过**的旧断言。

**如果发现 pi 的某个能力不如自建**：这是可以停下来的信号，不是硬扛的理由。停损点已定。
