Agent 聊天区 Markdown · 手搓解析器 vs 引库 对照设计稿

问题（用户提出）：聊天区正文本应把模型的 markdown 展示得"更完美"， 现在是自己手搓的解析器，是不是该换成现成的库？ 本稿先把实测缺口和两条路的真实成本摊开，再给建议 —— 决策权留给你。

所有"实测"数字都来自本机对 src/agent/markdown.js 的真跑，不是估计。

一、现状

  • 渲染器：src/agent/markdown.js，355 行，2026-10 之前写成。 文件头自述原因是「本机装不上 npm 依赖，仓库里也没有 markdown 库可复用」。
  • 复核（本次）：node_modules 里 marked / markdown-it / remark / micromark / DOMPurify / sanitize-html / highlight.js / prismjs 一个都没有， 也不在任何依赖的传递树里。也就是说"引库"必须先解决装依赖。
  • 宿主是浏览器扩展（MV3 语义），第三方代码必须打进 bundle， 不能远程加载 —— 体积直接影响 newtab 的包。

二、现状里三个"刻意"的设计（也是换库的代价所在）

① 转义优先

流程是「先 escapeHtml → 再做行内替换」。 正文全部来自模型，是不可信输入；这个顺序让 <script>、带 onerror 的 <img> 结构性地只能落成可见文本。 链接只放行 http/https/mailto，其余降级成纯文本。

这比"先渲染、再用 DOMPurify 过滤掉已知坏东西"强一档： 前者是"不可能发生"，后者是"过滤掉我们想得到的那几种"。

② 输出 token，不是 HTML 串

markdownToBlocks() 返回块数组（p / heading / code / list / table / quote / hr），由 Vue 模板逐个渲染。因此：

  • 每个代码块能挂自己的复制按钮（T-128）；
  • 表格委托给 AgentTable，带着 T-156 的溢出提示守卫；
  • 代码文本走 Vue 插值（自动转义），不需要 v-html。

库给的是 HTML 串 —— 这三样都要重造。

③ 流式增量解析

createMarkdownStream() 只重解析最后一个未完成块， 已完成的块缓存。实测（T-14，本机 node）：

  • 单次解析线性，约 0.55 ms / 万字（不掉帧）；
  • 整段重解析的累计成本随长度平方增长：20K 字按 40 字/delta 累计 313 ms，按 10 字/delta 1.1 s 主线程时间；
  • 只重解析最后一块：同样输入约 4 ms（约 70 倍）。

缺口 #2 的实测输出（最严重的一条）

输入

1. step
   - bullet

实际输出（内容被改写）

[{ "type": "list", "ordered": true,
   "items": [{ "html": "step - bullet", "depth": 0 }] }]
这不是"显示不够漂亮"，是语义被改变：两级结构塌成一句。 模型把要点写成嵌套列表时，用户看到的会和模型写的不是一回事。

五、两条路的成本对照

维度 方案 A · 原地补全缺口 方案 B · 换 marked + DOMPurify
新增依赖 0 2 个（marked、dompurify）+ 需先解决本机安装通道（历史上有"报成功但没写盘"）
bundle 体积 0 约 +60 KB min（marked ≈ 40 KB + DOMPurify ≈ 22 KB）
语法覆盖 会话正文的常见子集（上表 8 条全部可补） 完整 CommonMark + GFM，含脚注/定义列表等边缘语法
安全模型 转义优先生效 —— 保持"结构上不可能注入" 降档：库默认吐原始 HTML，安全从"不可能"变成 "DOMPurify 过滤得对不对"
token 接口 保留（复制按钮 / AgentTable 委托 / Vue 插值都不动） 需写自定义 renderer 把 blocks 再产一遍 —— 等于在库上面 重写一遍现在的模块
流式 保留增量（4 ms / 20K 字） 库无流式，每个 delta 重解析 → T-14 的 O(n²) 复发，需自包一层
守卫 增量补（给新补的语法各加一条） 16 条 markdown 守卫（含 5 条安全）按新契约重写
总体风险 低 中（装依赖 + 安全降档 + 三处重造）

六、建议

走方案 A（原地补全）。 理由：

  • 这个场景是"模型生成的会话正文"，真实流量是段落 + 列表 + 代码 + 偶尔表格。缺口集中在嵌套列表 / 混合嵌套 / 行内反引号 / 任务列表 —— 都能就地补，而且是几十行的改动。
  • 方案 B 换来的是"完整 CommonMark 合规"，代价是装依赖、+60KB、 把安全模型从结构性保证降成过滤，还要重造 token 接口与流式 两套已有的东西。收益与代价明显不成比例。
  • 真要上库，也应当先保留 token 接口（用库做 inline 解析、 自己出块结构），而不是直接 v-html 库的 HTML 串 —— 但那是另一个量级的工程。

方案 A 的落地清单（若采纳）

  1. 列表解析重写：depth 不再 Math.min(1, …)，按缩进推层级；
  2. 混合嵌套：有序项下的无序/有序子项不再当"续行"合并；
  3. 行内代码：支持 ``…`` 多反引号定界；
  4. 任务列表：- [ ] / - [x] → 复选框标记；
  5. 有序列表起始序号：<ol start="n">；
  6. 多段落列表项：缩进续段并回同一项，不留前导空格；
  7. 每条补一条守卫（沿用"每改必补"纪律），并跑变异验证。
