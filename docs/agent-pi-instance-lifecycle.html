pi Agent 实例生命周期分析

每轮对话重建实例（现状） vs 长驻复用 —— 代码层面的取舍证据

范围 src/agent/loop.js · index.js · provider.js · pi 包 日期 2026-10-10 方法 源码实测追踪
结论

现状不属于 pi 的最佳实践，但也不是 bug —— 它换到了「无状态可抛、切会话零漂移」。真正的问题只有一个：每轮重建时没有把 sessionId 传给 pi，等于主动放弃了 pi 唯一一条为「长会话缓存亲和」准备的通道。

但代码追到底后发现一个反直觉的事实：对我们的 BYOK 自定义端点，光补 sessionId 几乎不产生任何效果 —— pi 的缓存头与 prompt_cache_key 都被厂商/域名判定卡住，自定义端点不在放行名单里。所以「加 sessionId」不是那个划算的修复。

1. 现状如何运转（已核实）

每一轮 runtime.send() 都走一遍 createAgent()，而 pi 的 Agent 实例是在 createAgent 闭包里惰性创建的 —— 二者同生共死，所以实例的寿命恰好是「一轮」。

1
index.js:589 —— 每轮 send() 都 createAgent({...})
跨轮状态不在 runtime 里另存，每轮从 sessionStore.load() 现读历史（index.js:520-522）。注释原文：「两份状态必然漂移」。
2
loop.js:543 —— let piAgent = null; 闭包变量
注释明写：「每个 createAgent 一个，跨轮复用」。但 createAgent 本身每轮重建，所以这句「跨轮复用」实际只在同一轮内成立。
3
loop.js:810 —— piAgent = new Agent({...})
构造参数含 initialState / streamFn / transformContext / beforeToolCall。没有 sessionId。
4
loop.js:1025-1037 —— 历史重灌进 agent.state.messages
靠 historyToPiMessages() 把上轮的 agent 事件历史投影回 pi 的 transcript。这是跨轮续接的唯一机制。

pi 自己的设计意图（对照）

pi 的 README 第一行就是 「Stateful agent with tool execution and event streaming」，并且整条 API 都围绕「实例持有会话」来设计：

  • initialState.messages —— 构造时就该带上完整对话（不是构造完再覆盖）。
  • agent.state.messages —— 权威 transcript，可读可赋值。
  • reset()（agent.ts:355）—— 语义是「清空对话但保留 prompt/tool 基线」。作者预期的生命周期是：一个实例活很久，需要重开时 reset()，而不是 new Agent()。
  • sessionId（构造参数）—— 专门给 provider 做缓存亲和，只有实例长驻才谈得上意义。

2. sessionId 到 provider 的完整链路（实测）

第一轮里「sessionId 是否被传递」还是个推断。现已逐层读通，链路是通的 —— 唯一断点在最上游的构造处。

1
pi/agent/src/agent.ts:472 —— createLoopConfig() 里有 sessionId: this.sessionId
关键差异：ADR 0004 记的「pi 不转发 temperature / maxRetries」是真的，但 sessionId 被转发了。三者命运不同。
2
pi/agent/src/agent-loop.ts:403 —— streamFunction(model, ctx, { ...config, apiKey, signal })
整份 config 被展开，sessionId 随之下行到 streamFn。
3
src/agent/provider.js:134 —— 我们的 streamFn 把 ...options 展开进 streamSimple
这一层是透明转发的，不需要额外接线 —— 只要上游给了，它就会到。
4
pi/ai/src/api/openai-completions.ts:348 —— cacheSessionId = cacheRetention === "none" ? undefined : options?.sessionId
实测 resolveCacheRetention()（:294）默认返回 "short"（不是 "none"）→ 所以这里不会把 sessionId 抹掉。
5
openai-completions.ts:776 / :826 —— 用 sessionId 时被厂商判定卡住
见下一节。这是「补 sessionId 没效果」的根因。

3. 反直觉证据：BYOK 端点下 sessionId 几乎无效

pi 用 sessionId 做两件事，两件都有前置门 —— 而这些门对「自定义 OpenAI 兼容端点」全部关闭。证据在 openai-completions.ts：

门一：会话亲和头 —— 仅 OpenRouter

// :776
if (sessionId && compat.sendSessionAffinityHeaders) {
  if (compat.sessionAffinityFormat === "openrouter") {
    headers["x-session-id"] = sessionId;
  } else { /* x-client-request-id / x-session-affinity */ }
}

// :1680  默认值 —— 只有 OpenRouter 才是 true
sendSessionAffinityHeaders: isOpenRouter,   // isOpenRouter = provider==="openrouter" || baseUrl.includes("openrouter.ai")

我们的 buildModel(provider.js:69) 里 provider 取用户配置、baseUrl 是任意 BYOK 端点 → isOpenRouter 恒 false → 这一整块头都不会发。

门二：prompt_cache_key —— 仅 api.openai.com 或 long 保留

// :826
prompt_cache_key:
  (model.baseUrl.includes("api.openai.com") && cacheRetention !== "none") ||
  (cacheRetention === "long" && compat.supportsLongCacheRetention)
    ? clampOpenAIPromptCacheKey(options?.sessionId)
    : undefined,

我们既不是 api.openai.com，也没把 cacheRetention 设成 "long"（buildModel 根本不设这个字段，默认 "short"）→ 条件为假 → prompt_cache_key 恒 undefined。

门三（连带）：anthropic 风格 cache_control —— 同样不适用

// :1642
const cacheControlFormat = provider === "openrouter" && model.id.startsWith("anthropic/")
  ? "anthropic" : undefined;

// :1081  getCompatCacheControl()
if (compat.cacheControlFormat !== "anthropic" || cacheRetention === "none") return undefined;

只有「OpenRouter + anthropic/* 模型」才会挂 cache_control 块。我们的端点连这个分支都进不去。

综合：对我们的典型 BYOK 端点（自定义 baseUrl、非 OpenRouter、非 api.openai.com），把 sessionId 补上之后，pi 内部会拿到它、resolveCacheRetention 也不会抹掉它 —— 但走到实际 HTTP 请求时，没有任何一个字段会因此变化。收益 ≈ 0。

4. 两方案的取舍对照

维度方案 A 长驻实例 + reset()方案 B 保持每轮重建 + 补 sessionId
符合 pi 意图 ✅ 是 pi 预期用法（stateful + reset()） ⚠️ 仍偏离，只在参数上贴近
缓存亲和收益 ❌ 同样拿不到 —— 门在 provider 层，与实例寿命无关 ❌ sessionId 走到 HTTP 时被判定卡住，收益 ≈ 0
省掉历史重放 部分 —— 同会话续轮可省；切会话仍要 reset + 重灌 不变，仍每轮重放
切会话正确性 ❌ 风险点：需 reset() 再灌，漏 reset 会跨会话串味；systemPrompt 每轮变（facts 每轮重建）也要处理 ✅ 天然干净 —— 实例可抛，无残留
改动面 中 —— 改 createAgent 生命周期 + runtime 持有实例 + 切会话/切宿主 reset；动 countedUsage/harvestUsage 语义 极小 —— 两处加字段
测试影响 大 —— loop.test.js(79KB) 假设按轮新建 小

方案 A 的结构性摩擦（具体到代码）

  • 历史仍要从存储重灌。 index.js:652 的 initialHistory 是每轮从 sessionStore 现读的。即使实例长驻，只要真值在存储，就必须 reset() + 重灌 → 重放成本并没省掉，反而多了一层「实例状态 vs 存储」可能漂移的隐患（而那正是 index.js:513 注释想避免的事）。
  • systemPrompt 每轮变。 ensurePiAgent(systemPrompt) 只吃一个参数，systemPrompt 由每轮 facts 构建（loop.js:959-962）。长驻实例要处理「prompt 基线在活实例上如何更新」，pi 提供了 append system message 的机制，但那是新增接线。
  • usage 去重语义变化。 countedUsage（loop.js:578）是每闭包一个 Set，靠「按消息对象身份」去重。实例长驻后 pi 的 transcript 不再每轮清空，这套去重的假设要重新验证。
  • 切宿主 / 切会话要记得 reset。 agentHost.js 的切换流程没这动作，漏了就串会话。

5. 解决方案

推荐 · 分级处理

不为了一个拿不到的缓存收益去翻动实例生命周期

方案 B 的收益已被证据否定（≈0），方案 A 的收益不成立（门在 provider 层）+ 代价高（动生命周期与 79KB 测试假设）。所以正确的动作不是二选一，而是：

① 立即做（成本极低，消除「主动放弃」的观感）

  1. 把 sessionId 接上，并写清它是「为将来/他端点留的通道」而非当前收益。
    • createAgent 的 deps 加 sessionId；loop.js:810 的 new Agent 传入它。
    • 值用会话 id（currentSessionId，index.js:532 保证每会话有 id）。不要用 workflowId —— 一个工作流有多会话。
    • 注释必须照实写：「自定义 BYOK 端点下当前不会产生 prompt_cache_key / 亲和头（见 pi openai-completions.ts:776/826 的判定门）；接上它是为了 (a) 端点切到 api.openai.com/OpenRouter 时自动生效，(b) 避免每轮变化的值污染将来的缓存键。」 不许写成「修好了缓存」—— 那是假的。
  2. 在 buildModel（provider.js:69）补显式的 cacheRetention 决策（现在完全不设，默认 "short" 是隐式的）。若要 long 保留，需确认端点真支持，否则同样无效 —— 这也要注释写清依据。

② 观察后再定（不现在做）

  • 把「每轮 new Agent 的实测开销」与「重放历史的有损/成本」记成一条可观测的日志（turn.start 已有，加一个 replayedMessages 计数即可），跑一段时间看长会话下是否有真实痛点。
  • 只有当出现「长会话续轮明显变慢 / token 成本异常」的实测数据时，才启动方案 A 的评估。届时前提也应是「先和用户确认缓存端点」，而不是默认做。

③ 明确不做

  • 不做方案 A 的实例长驻 —— 在收益被证据否定、代价明确偏高的当前，它属于「以为在优化、实际引入新漂移面」的改动（与项目「不许看起来成功、实际什么都没做」的立场冲突）。
  • 不把「每轮重建」当 bug 修 —— 它是刻意的取舍，理由（无漂移）成立且写在 index.js:513。
一句话

「每轮新建 pi Agent」不是 pi 的最佳实践，但它换来的「无状态可抛」是本项目的合理选择；唯一的实际缺口是没传 sessionId —— 而证据显示，对当前 BYOK 端点补上它也几乎没用。所以：补字段 + 如实注释（成本低、防将来踩坑），不做生命周期重构。
