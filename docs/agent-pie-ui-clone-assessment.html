能不能复刻 pie 的界面？

对 pie-ai-agent 侧边栏 UI 的复刻可行性评估 + 可落地的设计稿 · 2026-10-10

一句话结论：能复刻「观感」，但不能（也不该）复刻「结构」。pie 的界面比本仓合理的部分集中在三条视觉决策上（灰度色阶、形态语言、动效纪律），这三条可以直接搬；但它整体之所以好看，还有一半来自 React 组件树 + 一整套独立产品形态（会话抽屉 / 六态顶栏 / 多视图），那部分是架构改动，不是复刻界面，代价远超「好看」二字。

三、逐条评价：哪些值得复刻，哪些是坑

✅ 值得复刻（三条，我建议做）

1. 三层底色色阶 —— 这是它「稳」的最大原因

pie 用了三个几乎相同、只差一点点的灰：

--c-canvas #FAFBFC最底（面板背景）
--c-surface #FFFFFF浮起来的卡（composer、抽屉）
--c-field #F4F6F8凹陷的输入区

本仓是 「一块白底 + 到处画边框」（border-gray-200 满天飞）。边框是最重的分隔手段，用得多了整屏都是线，反而吵。用 3% 的明度差代替 1px 边框是更高级的做法 —— 观感立刻从「拼装」变成「一体」。

代价：小。加 3 个 token + 把部分 border 换成 bg。不碰结构。

2. 语义化的暗色不是「反相」，是重新配的

左边亮色 --c-accent: #4A5C6E（灰蓝），暗色 --c-accent: #B8C8D6（亮灰蓝）。它不是把亮色调暗，而是重新选了一个在深底上才成立的亮色。本仓的暗色基本是亮色的反相，所以 dark 下经常「灰得发闷」。

代价：小。就是那 20 个变量的暗色列重配一遍。

3. 动效纪律：一条曲线、一个时长区间

pie 通篇只有 cubic-bezier(0.32,0.72,0,1) + 150–250ms。我做 T-200 时已经把这套 token 搬过来了（ease-panel / duration-fast/base/slow），但只用在 3 个 transition 上，覆盖面远不如它。

代价：小。把剩下的 transition 都挂上 token 即可，已有守卫兜底。

⚠️ 可以借鉴形态，但要注意代价（四条）

4. 顶栏「一个栏、六个态」

pie 只有一条顶栏：会话态显示 [☰][＋] 标题 [⏰][🔭][⚡]，进设置就变成 [←] 设置标题。本仓现在是 每个视图各有一个 header，所以切视图时头会重排。

评价：可以学思路，但别照搬内容。 pie 的 [⏰ 定时][🔭 研究][⚡ 技能] 是它有、本仓没有的视图；照搬会得到三个点不动的按钮。能学的只有「用一条栏承载所有态」这个原则 —— 而我做 T-207 时把 chat/history 两个 header 合成一个 chip，已经是在往这个方向走了。

代价：中。要动 AgentPanel.vue 的视图切换逻辑。

5. 会话列表做成「从底部上滑的抽屉」

pie 点 ☰ 时会话列表从底部滑上来盖住全屏；本仓是「整块替换正文区」。抽屉的好处是不卸载正文（滚动位置保留）。

评价：形态可借，但收益看场景。 本仓的历史视图用整块替换，注释里（AgentPanel.vue:143-149）已记录了这个选择的代价。抽屉能省掉一次卸载/重挂，但 Chrome 侧栏高度本来就矮，从底部滑出会显得局促。

代价：中。

6. 步骤行（step line）而不是「工具卡」

pie 把工具调用渲染成一行很轻的 › 读取页面 · 找到 3 个表格（mono 10–11px，无边框）；本仓是带边框的折叠卡。

评价：这是**真差异**，但方向要对。 工具卡是本仓的有意设计——工具调用的参数/观察值是排查问题的关键（T-174/T-175 花了大力气做它的溢出与字号）。pie 轻量化是因为它偏「消费者」，本仓偏「工作流自动化工具」的一个部件，信息密度需求不同。建议不照搬，但可以借鉴「未展开时更像一行」。现有折叠态已经是这个思路。

代价：小（改折叠态样式），但可能倒退可调试性。

7. 圆点网格底纹（dot-grid）

radial-gradient 24px 网格，4–5% 透明度。

评价：好看，但它是**品牌资产**不是设计模式。 那个点阵和 pie 的 IP 形象配套。本仓搬过来会显得莫名其妙 —— 除非你想给助手也做一个「图形身份」。

代价：极小（一行 CSS），但含义不对。

❌ 不建议复刻（三条）

8. 五个并列视图（agent / schedules / research / skills / settings）

这是 pie 作为独立产品的形态。本仓的助手是工作流编辑器里的一个面板（还有三个宿主共用），塞五个视图进去 → 侧栏装不下，而且「定时/研究/技能」在本仓是别的东西。

9. 会话的 paused / failed / archived 状态机

pie 的抽屉里每条会话有状态、可恢复、可归档。这是数据模型，不是 UI —— 本仓的会话模型简单得多，硬加上去要做存储迁移。

10. 图片渲染 / KaTeX 公式

这是本仓刻意砍掉的：markdown.js:112-114 把图片降级为 alt 文本，有安全依据（页面内容一律 untrusted）。搬 KaTeX 等于把一个渲染面重新打开。

四、我的建议：分两步，先做 ①，②③ 只借原则

第一步（建议现在做，低风险）：搬「观感三件套」
三层底色阶 + 暗色重配 + 动效全覆盖。改动集中在 tailwind.config.js 与 tailwind.css 的 token 层，不碰任何组件结构。做完之后你会立刻觉得「像了」，而这是收益/风险比最高的一步。
第二步（要你决定，中风险）：借「形态原则」但不搬「内容」
顶栏统一成一条（本仓已走了一半）、抽屉式会话列表（可选）。这一步要动 AgentPanel.vue，有回归风险，建议单独排期。
不要做的：把 pie 的五个视图、会话状态机、KaTeX、IP 底纹搬进来 —— 那些不是「界面更好看」，是「换一个产品」。收益是观感，代价是架构。

一个必须提醒的坑：本仓的旧守卫锚的是具体 class 串（例如 border-gray-200 dark:border-gray-700）。一旦把边框换成底色，一批守卫会连锁变红。这不是守卫坏，是它在如实报告「视觉语言变了」——就像我做 T-207 时 T-172/T-187 同时报红那样。所以这一步要逐条判断「是回归还是有意迁移」，不能批量改正则。

七、结论

  • 能复刻的是「观感」 —— 三条视觉决策，收益高、风险低，我建议做。
  • 「形态」可以借原则，但 pie 的六个顶栏按钮/五个视图是它的产品内容，搬进来会是空壳。
  • 「架构」不要碰 —— 那是换产品，不是改界面。
  • 你现在的界面「不如它合理」的主要落差在配色与层级（靠边框而非底色），不在结构。修这一处的性价比，远高于重做结构。
下一步：如果你认同，我可以先只做第一步（观感三件套）—— 改 token 层 + 把边框分层替换，不碰任何组件结构，做完给你一份前后对比。这一步预计会让面板「一眼变好」，且不引入结构风险。要不要做、做多大范围，你定。
